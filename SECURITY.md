# SECURITY.md — EventSphere Authentication

Security posture, controls, and tradeoffs for the authentication system.

## Guiding principle

Priority order: **Security > Correctness > Reliability > UX > Convenience.** The
backend is the only authority. Nothing from the React client is trusted — not role
claims, not `localStorage`, not request bodies, not URL parameters.

## Password policy (authoritative, server-side)

Enforced by ASP.NET Core Identity:

- Minimum length **12**
- Requires uppercase, lowercase, digit, and non-alphanumeric
- At least **4 unique** characters

Client-side checks in the React app are UX only.

## Account lockout (brute-force protection)

- **5** failed attempts → locked for **15 minutes** (`Lockout.AllowedForNewUsers = true`).
- Lockout is per-account. Tradeoff: an attacker who knows an email can force that one
  account into a 15-minute lockout (targeted DoS). We accept this over unlimited
  guessing; login is also IP-rate-limited. A more DoS-resistant scheme (e.g. risk-based
  or CAPTCHA) is a possible future enhancement.

## Rate limiting

Built-in ASP.NET Core rate limiter, partitioned by client IP:

- **Auth policy** (`register`, `login`, `refresh`, external init): `AuthPermitLimit`
  requests per `AuthWindowSeconds` (default **10 / 60s**) — deliberately strict.
- **Email policy** (`forgot-password`, `resend-verification`, `reset-password`):
  `EmailPermitLimit` requests per `EmailWindowSeconds` (default **5 / 60s**) — strictly
  separate from auth limits to prevent email abuse and bombing.
- **General limiter**: default **100 / 60s** for all other traffic.
- Rejections return **429** with a `Retry-After` header and a generic JSON message.
  Values are configurable under `RateLimiting` and documented; no undocumented limits.

## Email enumeration protection

- **Login**: returns the same `401 "Invalid email or password."` whether the email is
  unknown or the password is wrong.
- **Forgot password**: always returns the same generic response regardless of whether
  the email exists: "If an account exists for this email, we sent a password reset link."
- **Resend verification**: always returns the same generic response regardless of
  whether the email exists.
- **Registration**: returns `409` on duplicate email (standard, accepted enumeration
  surface).

## Email verification security

- Tokens are generated by `UserManager.GenerateEmailConfirmationTokenAsync` —
  cryptographically secure, Identity-managed.
- Tokens are single-purpose (email confirmation only).
- Tokens expire according to Identity's configured confirmation token lifespan.
- Tokens are validated server-side via `UserManager.ConfirmEmailAsync`.
- Resend verification is rate-limited via the `email` policy.
- No custom token generation — relies entirely on Identity's secure implementation.

## Password reset security

- Tokens are generated by `UserManager.GeneratePasswordResetTokenAsync` —
  cryptographically secure, Identity-managed.
- Tokens are single-purpose (password reset only).
- Tokens expire and cannot be reused after successful password reset.
- The forgot-password endpoint never reveals whether an email exists.
- After password reset, **all existing refresh tokens are revoked** — the user must
  re-authenticate with the new password.
- Strong password validation is enforced during reset (same policy as registration).
- `UserManager.ResetPasswordAsync` is used — never manual password hash updates.
- Password reset tokens are never logged.
- Reset URLs redirect only to configured `Frontend:AllowedOrigins` — no open redirects.

## Brevo secret management

- Brevo API key, sender email, and sender name are configured via:
  - Environment variables (`BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME`)
  - User Secrets / Secret Manager
  - `appsettings.json` with placeholder values only
- **Never committed**: API keys, sender credentials, real secrets
- **Never logged**: Brevo API key is never written to logs, error responses, or output
- Failures are logged server-side with diagnostic info (status code, error body) but
  the API key is never included in log output

## OAuth security

- CSRF/state and (for Google) PKCE are handled by the OAuth handler; correlation
  cookies are set. Callback paths are fixed (`/signin-google`, `/signin-github`).
- **Open-redirect protection**: the backend never redirects to a client-supplied URL.
  Post-login redirects always target a configured `Frontend:AllowedOrigins` origin +
  a fixed path. `?returnUrl=` is not honored.
- Password reset URLs redirect only to configured `Frontend:AllowedOrigins` —
  no arbitrary redirect targets.
- **Account linking** requires a provider-verified email and refuses to attach a
  provider to a pre-existing account without explicit linking (see AUTHENTICATION.md).
- Minimum scopes requested: Google `openid profile email`; GitHub `read:user user:email`.

## CORS

- Explicit origins only, from `Frontend:AllowedOrigins`. **`AllowAnyOrigin()` is never
  used.** `AllowCredentials()` is enabled so the refresh cookie can flow; this is
  incompatible with a wildcard origin by design.

## HTTP security

- `UseHttpsRedirection` always; **HSTS** in non-Development.
- Security headers on every response: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a locked-down
  `Content-Security-Policy` (`default-src 'none'; frame-ancestors 'none'`), and
  `X-Permitted-Cross-Domain-Policies: none`.
- Refresh cookie: `HttpOnly`, `Secure` (when SameSite=None or the request is HTTPS),
  `SameSite` configurable (`None` for cross-site SPA→API, `Lax`/`Strict` for same-site).

## JWT security

- Access tokens are short-lived (15 min) with strict validation: issuer, audience,
  signature, lifetime, key; `ClockSkew = 0`.
- No sensitive PII in JWT claims (no passwords, no refresh tokens, no internal IDs
  beyond the user's integer PK).
- Signing key comes from `Jwt:Key` (env vars / user secrets). Development generates
  an ephemeral key if none is set; production requires a key ≥ 32 bytes.

## Refresh token security

- Random 256-bit values, stored only as SHA-256 hashes in the database.
- Rotated on every use; family-wide revocation on reuse detection.
- HttpOnly, Secure, SameSite cookie scoped to `/api/auth`.
- 7-day expiry; revoked on logout.
- **Bulk revocation**: password reset revokes all tokens for the user.

## Authorization

- Enforced server-side with `[Authorize]` / `[Authorize(Roles=...)]` reading Identity
  roles carried as signed `role` claims. Editing `localStorage`, JWT claims, React
  state, request bodies, or URLs cannot grant a role — a tampered token fails signature
  validation, and roles are resolved from the database at token issuance.
- React route guards (`ProtectedRoute`) and hidden UI are **UX only**.

## Admin protection

- Normal registration cannot create an Admin. Users cannot self-promote. Organizers do
  not gain Admin. No public promotion endpoint exists.
- An optional development-only admin can be seeded via `SeedAdmin` configuration
  (disabled by default; credentials come from env vars / user secrets, never source).

## Error handling

- A global exception handler returns a generic `500` JSON body; full details are logged
  server-side only. Responses never contain stack traces, SQL text, internal type names,
  tokens, or secrets. Validation failures return a consistent `{ success, message, errors }`
  shape with per-field messages.
- Brevo API errors are never exposed directly to users — safe API errors are returned
  instead.

## Secrets

- No secrets in source. `Jwt:Key`, Brevo API key, OAuth client secrets, DB credentials,
  and the seed admin password come from environment variables / User Secrets / a secret
  manager.
- **Known issue**: `appsettings.Development.json` currently contains a local SQL
  connection string with a password (set for local convenience). Move it to User Secrets
  and rotate it; treat any previously committed secret as compromised and rotate it.
  `appsettings.Production.json` and `.env` are git-ignored.
